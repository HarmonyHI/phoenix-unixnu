## 20:35-20:55 崩溃定位与 FV 载荷修复
- 现象：带载荷固件一律 10 秒内复位/异常 dump（ASSERT ArmCpuDxe CpuExceptionHandlerLib.c(438)），无载荷镜像"看似能跑"其实复位进 Android。
- 关键修复 1：`mkinitrd.sh` 丢了 DTB 追加（01:14 git checkout 回退时带走），导致 SEC 拿不到设备树、只出一行 `splitting block entry with MMU disabled` 就重启。补回后固件活了（DTB 398,781 B 追加在 gzip kernel 后）。
- 关键修复 2：UniXNURamDiskDxe 入口 no-HOB 分支先读 FV 内嵌载荷、DRAM 扫描表重排（0x8AB00000 窗口提前、HYP 移到末尾）。
- 关键修复 3（根因）：`Fv2->GetNextFile` 的 `FileType` 是输入过滤，必须初始化为 0（EFI_FV_FILETYPE_ALL）；未初始化的栈垃圾导致循环一次就 EFI_NOT_FOUND → "no embedded payload in firmware"。已修，`Type = 0; Key = 0;`。
- 验证方法：固件内部结构确认载荷 FFS 6A1D2C33 在 LZMA 压缩的 FvMain 内（内层 blob 6,529,032 B，载荷偏移 4,606,716）；加 STEP 标签打印逐阶段定位。
- 排查技巧：`fastboot boot` 连续 Load Error 时先 `fastboot reboot-bootloader`；`fastboot devices` 为空 ≠ 固件在跑（可能已复位进 Android）。
- 产物：Mu-phoenix-fv.img / fv2.img / fv3.img（fv3 为修复 GetNextFile 后待验证版，5,699,584 B）。
